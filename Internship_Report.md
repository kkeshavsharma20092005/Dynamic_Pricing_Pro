### 4.4 Final Project: Dynamic Pricing Optimization Engine (In Detail)

#### Problem Statement

Setting prices manually in industries like ride-hailing, e-commerce, and hospitality is inherently suboptimal -- static prices fail to account for fluctuating demand, competitor behaviour, weather conditions, and time-of-day effects. Over-pricing drives customers away; under-pricing leaves revenue on the table. The challenge is that **no historical dataset contains "optimal prices"** -- past prices were set by humans or static rules, and training a model on them would only learn to repeat past mistakes.

#### Goal

Build an end-to-end Dynamic Pricing system that (1) predicts demand as a function of price and contextual features using a Machine Learning model, and (2) uses a price optimizer to sweep candidate prices and find the one that maximises profit -- deployed as a production-shaped full-stack application with a REST API and a live interactive dashboard.

#### Core Architecture: Why Two Steps, Not One

The key insight driving this project is the **separation of prediction and optimization**:

1. **Demand Model (ML)** -- Answers: *"At price P, in this context, how many units will sell?"*
2. **Price Optimizer (Arithmetic)** -- Sweeps 121 candidate prices, asks the model that question for each, and returns the price maximising `(price − cost) × demand`.

Step 2 is deliberately *not* machine learning -- it is an auditable grid search over a predicted demand curve. This separation ensures the system is explainable and trustworthy.

#### Dataset

**14,600 synthetically generated hourly records** across 5 product SKUs (vehicle tiers), with the following features:

| Feature | Description |
|---------|-------------|
| **hour** | Hour of day (0--23) |
| **day_of_week** | Day of the week |
| **is_weekend** | Weekend indicator |
| **weather** | Weather condition (Clear, Rain, Fog) |
| **temperature** | Temperature in degrees Celsius |
| **competitor_price** | Competitor's current price |
| **base_price** | Product's base/cost price |
| **price** | Actual price charged |
| **demand** | **TARGET** -- units demanded at that price and context |

**Why synthetic data?** The generator builds demand from a *known* elasticity (−1.79) that the model is never shown. Unlike real data, this lets us verify whether the model actually recovers the correct price-demand relationship -- not just whether it fits the data well.

#### Data Pipeline and Feature Engineering

```python
# Generate 14,600 rows across 5 SKUs with known ground-truth elasticity
# Feature engineering: 38+ features including:
# - Cyclical time encoding (sin/cos of hour, day_of_week)
# - Price ratios (price / competitor_price, price / base_price)
# - Lag features (demand_lag_1h, demand_lag_24h)
# - Interaction terms (price × weather, price × hour_bucket)
# - Rolling statistics (demand_rolling_mean_6h)

from sklearn.model_selection import GridSearchCV
from sklearn.linear_model import Ridge

# Model selection with GridSearchCV
param_grid = {'alpha': [0.01, 0.1, 1.0, 10.0, 100.0]}
ridge = GridSearchCV(Ridge(), param_grid, cv=5, scoring='r2')
ridge.fit(X_train, y_train)
```

#### Model Selection: Why Ridge Regression Beat Random Forest

Three models were trained and evaluated on a chronological holdout (last 20% of hours, never seen during training):

| Model | RMSE | R-squared | Elasticity | Recovers Truth? | Decision |
|-------|------|-----------|------------|-----------------|----------|
| **Ridge Regression** | **6.80** | **0.924** | **−1.91** | **Yes (err 0.12)** | **Selected** |
| Gradient Boosting | 8.17 | 0.891 | −1.47 | Yes (err 0.32) | — |
| Random Forest | 10.80 | 0.809 | −0.59 | No (err 1.20) | **Rejected** |
| Baseline (mean) | 29.23 | −0.401 | — | — | — |

**The critical insight:** Random Forest scored a respectable R-squared of 0.81 but was **useless for pricing** -- its estimated elasticity was −0.59 when the truth was −1.79. It forecast demand well by leaning on lag features while barely responding to price changes. Shipping it would mean the optimizer climbs a nearly flat curve, systematically under-correcting prices while the dashboard displays a healthy R-squared.

**Models are therefore gated on elasticity, not RMSE.** A model that cannot reliably produce a downward-sloping demand curve is rejected regardless of forecast accuracy.

#### Ground-Truth Validation by Segment

| Segment | Estimated Elasticity | True Elasticity | Error |
|---------|---------------------|-----------------|-------|
| Rush hour (07--09, 17--19) | −1.63 | −1.54 | 0.08 |
| Off-peak (22--05) | −2.09 | −2.07 | 0.02 |
| Raining | −1.67 | −1.59 | 0.08 |
| Dry | −1.99 | −1.96 | 0.03 |

**Per-row correlation with ground truth: r = 0.870, MAE = 0.134.** The model discovered on its own that commuters in the rain barely look at price -- the surge opportunity a static price leaves on the table.

## Chapter 6. Challenges Faced

### 6.1 Technical Challenges

1. **Data Cleaning Complexity:** Real-world datasets had inconsistent formats (e.g., engine size stored as "1248 CC" instead of a pure number, power as "82 bhp" with units attached). Learning to use string operations (`.str.replace()`, `.astype()`) to clean these was initially challenging but became second nature through repeated practice.

2. **Handling Missing Values:** Deciding whether to drop rows with missing values or impute them required understanding the data context. For the dynamic pricing dataset, engineering lag features required careful handling of edge cases at time-series boundaries to avoid introducing data leakage.

3. **Feature Encoding:** Understanding when to use Label Encoding vs. Target Encoding vs. One-Hot Encoding was confusing at first. The key insight was that Target Encoding works well for high-cardinality features (like car brand names with 30+ categories) where One-Hot Encoding would create too many columns.

4. **Overfitting in Tree Models:** Early Random Forest models with no depth limit memorized the training data (R-squared ~0.99 on train, ~0.85 on test). Learning to cap `max_depth=14` and use proper train-test evaluation was an important lesson in model generalization.

5. **Group Project Complexity:** The Dynamic Pricing Engine was significantly more complex than individual projects -- understanding econometric concepts like price elasticity, endogeneity, and the distinction between prediction accuracy and causal validity was challenging but deeply educational.

### 6.2 Communication and Team Challenges

6. **Coordinating Group Work:** Dividing responsibilities for the Dynamic Pricing Engine among three team members required clear communication about module interfaces (e.g., ensuring the feature engineering code was consistent between training and the live API).

7. **Presentation Skills:** Delivering the group presentation on Recommendation Systems required distilling complex concepts into clear, accessible slides -- a different skill from writing code.

# Price Optimizer: 121-point grid sweep
def optimize_price(model, context, base_price, cost):
    prices = np.linspace(base_price * 0.7, base_price * 1.4, 121)
    demands = model.predict([context + [p] for p in prices])
    profits = (prices - cost) * demands
